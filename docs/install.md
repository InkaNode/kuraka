# Install

One VPS runs three containers from [deploy/](../deploy):

| Service | Public ports | Role |
|---|---|---|
| `caddy` | 80, 443, 443/udp | HTTPS for the panel and Stalwart's public HTTP paths; obtains the certificates |
| `stalwart` | 25, 465, 993 | SMTP, SMTPS, IMAPS. HTTP (8080) is private; `/admin` and `/login` return 404 through Caddy |
| `kuraka` | none | panel and API behind Caddy, SQLite in the `kuraka_data` volume |

All three share the Docker network `kuraka_mail` (172.30.0.0/24). Libredesk bundles generated by Kuraka join it as an external network.

## Requirements

- A VPS with 2 GB of RAM or more, Docker Engine with the Compose plugin, `curl`, `jq` and `openssl`.
- Inbound ports 25, 80, 443 (TCP and UDP), 465 and 993 open.
- **Outbound port 25 open.** Many providers block it by default; ask them to lift the block, or mail will not leave the server.
- DNS A records (and AAAA if you use IPv6) pointing to the VPS:
  - `PANEL_HOST`, e.g. `panel.example.com`.
  - `MAIL_HOST`, e.g. `mail.example.com`. With Cloudflare, **proxy OFF** (grey cloud) for this name: SMTP and IMAP cannot go through the proxy.
- A PTR (reverse DNS) record for the VPS IP equal to `MAIL_HOST`, set at the VPS provider.

## Quick start

```sh
git clone https://github.com/InkaNode/kuraka.git
cd kuraka
cp deploy/.env.example deploy/.env
nano deploy/.env        # PANEL_HOST, MAIL_HOST, MAIL_DOMAIN, ACME_EMAIL
bash deploy/setup.sh
```

`setup.sh` is safe to re-run. It:

1. Generates `KURAKA_SECRET_KEY` and `STALWART_RECOVERY_ADMIN` in `deploy/.env` (mode 600).
2. Starts Caddy and Stalwart and waits up to 5 minutes for the `MAIL_HOST` certificate.
3. Bootstraps Stalwart through JMAP (hostname, default domain, DKIM keys), stores the returned admin as `STALWART_ADMIN`, registers Caddy's certificate for SMTP/IMAP and creates the Kuraka API key (limited to the `kuraka_mail` subnet, without domain-destroy, listener and role permissions). It also points Stalwart's web interface to the [InkaNode/stalwart-webui](https://github.com/InkaNode/stalwart-webui) build, which hides the views Kuraka manages and Enterprise-only views until "Show Kuraka and Enterprise items" is turned on in the user menu.
4. Starts Kuraka and prints the one-time setup token.

Then:

1. Open `https://PANEL_HOST/#/setup` and create the superadmin with the token.
2. Set the PTR record if you have not yet.
3. In Kuraka, assign `MAIL_DOMAIN` (and any other domain) to a tenant and publish its DNS records, through Cloudflare or by hand.
4. Rotate `STALWART_ADMIN`, remove `STALWART_RECOVERY_ADMIN` from `deploy/.env` and run `docker compose -f deploy/docker-compose.yml up -d stalwart`.

### Certificates for SMTP and IMAP

Caddy obtains the certificate for `MAIL_HOST`; Stalwart reads it from the shared `caddy_data` volume (read-only) at `/caddy-data/caddy/certificates/acme-v02.api.letsencrypt.org-directory/MAIL_HOST/`. `setup.sh` makes only that key readable by the Stalwart group.

Caddy renews the certificate in place, but Stalwart reads it at startup. Add a weekly job that fixes the permissions and restarts Stalwart:

```sh
echo '17 4 * * 1 root bash /opt/kuraka/deploy/setup.sh refresh-cert >/dev/null' | sudo tee /etc/cron.d/kuraka
```

The `x:Certificate` "File" shape is taken from the Stalwart docs and not yet verified on a live server. After the first run, check that IMAP presents the Let's Encrypt certificate:

```sh
openssl s_client -connect MAIL_HOST:993 -servername MAIL_HOST </dev/null | openssl x509 -noout -issuer -subject
```

If Let's Encrypt fails, Caddy may fall back to ZeroSSL and store the files under another issuer directory; fix the DNS and restart Caddy.

## Firewall

Ports published by Docker bypass `ufw` and `firewalld` rules: Docker writes its own iptables rules. Filter at the provider's firewall, or in the `DOCKER-USER` chain. The stack never publishes 8080; do not add it.

## Upgrades

```sh
cd kuraka && git pull
cd deploy
docker compose pull
docker compose up -d
```

Pin `KURAKA_VERSION` in `deploy/.env` to a release tag for predictable upgrades, and read [CHANGELOG.md](../CHANGELOG.md) first.

## Backups

Volumes (Compose prefixes them with the project name `kuraka`):

| Volume | Contents |
|---|---|
| `kuraka_kuraka_data` | Kuraka SQLite: tenants, users, sessions, audit, encrypted secrets |
| `kuraka_stalwart_data` | mailboxes and Stalwart's database |
| `kuraka_stalwart_etc` | Stalwart configuration |
| `kuraka_caddy_data` | certificates and ACME account |

Also back up `deploy/.env`: without `KURAKA_SECRET_KEY` the encrypted secrets (TOTP, Cloudflare tokens, Libredesk credentials) cannot be read.

The Kuraka image is distroless, so `docker compose exec kuraka sqlite3 ... ".backup ..."` is not available. Stop Kuraka and Stalwart for a consistent copy; it takes seconds:

```sh
cd deploy
mkdir -p backups
docker compose stop kuraka stalwart
for v in kuraka_data stalwart_data stalwart_etc caddy_data; do
  docker run --rm -v "kuraka_$v:/v:ro" -v "$PWD/backups:/b" alpine \
    tar czf "/b/$v-$(date +%F).tar.gz" -C /v .
done
docker compose start stalwart kuraka
cp .env "backups/env-$(date +%F)"
chmod -R go-rwx backups
```

Restore by extracting each archive into an empty volume of the same name before `docker compose up -d`. Keep backups off the server and encrypted.

## Libredesk bundles

A superadmin downloads a bundle per tenant from Kuraka (`GET /api/v1/helpdesks/bundle`). On the VPS:

```sh
unzip libredesk-<tenant>.zip -d /opt/libredesk-<tenant>
cd /opt/libredesk-<tenant> && docker compose up -d
```

The bundle joins `kuraka_mail`, so its container reaches Stalwart and is reachable by Caddy as `kuraka-<tenant>-app-1:9000`. Copy the desk block from `deploy/Caddyfile` into `deploy/sites/desk.caddy` with your hostname, add its DNS A record, run `docker compose restart caddy`, then register the instance in Kuraka.

## Security notes

- Rotate `STALWART_ADMIN` after setup and remove `STALWART_RECOVERY_ADMIN`; keep them out of shell history and tickets.
- Keep Stalwart's 8080 private. The admin interface is only reachable from the Docker network, e.g. through an SSH tunnel to a temporary container.
- `deploy/.env` holds every secret of the stack: mode 600, owned by root, never committed.
- The Kuraka API key is accepted only from 172.30.0.0/24. Containers you add to `kuraka_mail` share that subnet; only attach trusted services.

## Troubleshooting

- **Clients or Kuraka suddenly cannot connect.** Stalwart blocks IPs that look like port scanners or brute-force sources. Inspect and lift blocks with the `x:BlockedIp` objects, and add trusted addresses (your office, monitoring) as `x:AllowedIp`.
- **Deleting a domain in Stalwart fails.** Its DKIM signatures (`x:DkimSignature`) must be destroyed first. The Kuraka API key cannot destroy domains by design; use the Stalwart admin.
- **No certificate after 5 minutes.** Check the A records, that the Cloudflare proxy is off for `MAIL_HOST`, that ports 80/443 are reachable, and `docker compose logs caddy`.
- **Kuraka exits at startup.** `docker compose logs kuraka` lists every invalid or missing `KURAKA_*` variable.
- **Outgoing mail is rejected or lands in spam.** Check the PTR record, outbound port 25, and the DNS check page in Kuraka (SPF, DKIM, DMARC, MX).
